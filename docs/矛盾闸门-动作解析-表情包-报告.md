## 1. 问题一（最严重）：模型否认 + 和系统回执自相矛盾

### 真机证据（GBK 日志按 UTF-8 解码后）
- `data/live.err` 22:20:23：模型说「私聊这边春禾没法直接推消息到群里」，而 22:20:21 引擎刚把 `@群友` 真发到群（回执 `已经发到群里啦`）。
- `data/live.err` 22:22:37：模型说「表情包好像只能发在当前这个窗口里，春禾没法把它直接转到群里去」，紧接着引擎回执「已经发到群里啦～（大群 9F42…）」——**同一句回复里前后打架**。

### 机制：代码闸门（不是提示词建议）
新增 `engine.js: guardCapabilityContradiction(text, { evidence, receipt })`，与既有
`guardUnbackedPromise`（假承诺闸门）并列、复用同一套理念，**不重复造轮子**：

1. 复用并扩展 `CAPABILITY_DENIAL_PATTERNS` / `detectCapabilityDenial`（原函数保留，
   仍用于统计与告警），新增三条覆盖这次原话的规则：
   - `没法…(转|发|推|送)…群`
   - `只能发/留…当前|这个窗口/会话/聊天/私聊`
   - `私聊这边…(没法|不能|做不到)`
2. 只有**引擎确定性知道结果**时（`proactiveDelivery?.ok === true`）才动手：
   命中否认 → **整段模型文字换成确定性回执**（`describeProactiveDelivery`，
   例如「表情包已经发到群里啦～（大群 9F42… · 至少 8 位发言人…）」）。
   没有回执（失败/没有群/配额）→ 不替换：保留模型的话，由假承诺闸门删掉
   「已经发了」，再由失败回执如实说没发出去。
3. 顺序很关键：先 `guardUnbackedPromise`（删无证据的成功承诺）→ 再
   `guardCapabilityContradiction`（有证据时删否认）。两者不会互相抵消。
4. 新增统计 `stats.capabilityContradictions`，命中会打 WRN：
   `模型否认了已经做到的事…已用确定性回执替换`。
5. 提示词同步加硬规则 2.7：「回执是事实，不许和它打架」，并把「群里发下 /
   发个表情包 / 看看你卖萌的样子」写进能力清单（只是减少发生率，**兜底仍是代码闸门**）。

为什么选「替换」而不是「只删矛盾句」：22:22 那句删掉否认后剩下的
「主人在群里说一句卖萌，春禾就在群里发给你看」本身也在否定“已经发过”，
仍会和回执打架；回执本身就是完整的一句人话，整段替换最不会自相矛盾。

## 2. 问题二：「群里发下」被解析成动作「发下」并真的发到群里

### 修复（`src/core/pending-actions.js`）
`classifyPendingAction` 重写了「发」类分支：

| 输入 | 解析结果 |
|---|---|
| 群里发下 / 在群里发个表情包 / 群里发表情 / 群里发个贴图 | `payload.sticker: true`（发贴纸，动作名规范成「发个表情包」） |
| 在群里发个消息说该开会了 | `kind: "say"`，`payload.text: "该开会了"` |
| 群里发一下 / 群里发个 / 群里发个消息 | `needsConfirm: true`，只存草稿，**先问清楚，不发** |
| 你能在群里说话吗 | 仍按能力询问丢弃（回归保持） |

- 动词残片（`下/一下/个/点/话/消息…`）**永远不会**成为消息内容。
- 贴纸待办走新加的主动投递分支：`#deliverPendingProactively` 里
  `payload.sticker` → `executeStickerCall` 选图 → `uploadMedia("group",…)` +
  `sendMedia("group",…)`；失败返回 `sticker_unavailable` 并如实说没发，
  保留待办、不烧配额。成功回执是「**表情包**已经发到群里啦～」。
- 兜底：素材缺失时回执明确说「素材还没准备好，这次没发到群里，没骗主人」。

## 3. 问题三：「看看你卖萌的样子」只回文字

### 说明（诚实）
`live.log` 22:22:16–22:22:21 实际有：
`发送表情包：春禾-卖萌` → `已生成 1 张图片` → `已发送图片 1/1` → `已回复 c2c（20 字）`。
也就是说**那一刻模型确实调了 `send_sticker` 且图片发出去了**，
「只回文字」无法从这份日志完整复现；但发不发依赖模型掷骰子，本身不可靠。

### 修复：引擎确定性触发（不再靠模型选工具）
- `stickers.js` 新增 `detectStickerRequest(text)` 与 `pickStickerName(list, req)`：
  - 「看看你卖萌的样子」→ `{keyword:"卖萌"}` → 命中「春禾-卖萌」；
  - 「发个比心」→「春禾-比心」；「发个你的表情包 / 发表情 / 发个表情包」→ 通用，优先「春禾-开心」；
  - 问数量/问能力（几个、能不能）、否认句、闲聊 → 不触发；优先「春禾-」自家素材，不拿猫图糊弄。
- `engine.js` 在生成回复前算好 `stickerPlan`（复用 `executeStickerCall`），
  通过 `ctx.stickerPlanned` 注入人格层提示「系统已经发了，不要再调 send_sticker，也别说发不了」；
  回复时把图交给既有 `#sendImages`（先图后文，图片失败不影响文字）。
- 私聊里刚记下的跨场景待办不会误发到私聊（`!queuedPending` 才发），
  「群里发下」仍由待办主动投递负责。

## 4. 群聊能不能发表情包？——验证结果

新增 `scripts/check-capfix.mjs`，A 段用**真实 `QQApi` + 假 fetch**（与
`check-song-group.mjs` 同法）跑真实引擎，断言真实 URL 与请求体：

```
✔ POST /v2/groups/GROUP_CAPFIX_90A0/files      （file_type=1，body 带 base64）
✔ POST /v2/groups/GROUP_CAPFIX_90A0/messages   （msg_type=7，body 带 file_info）
✔ 没有误走 /v2/users/…
```

结论：群聊表情包走的是 `#sendImages` 早已在用的分场景 `uploadMedia(msg.scope, …)`，
路径与群里唱歌/发图完全同一条，**代码链路通**。

**未验证的部分（诚实）**：没有向真实 QQ 发任何消息。因此「平台是否允许
不带 msg_id 的主动富媒体（待办贴纸投递）」只有失败兜底、没有线上成功证据；
若平台拒绝，回执会如实说没发出去（不会假装）。普通回复里的群表情包是
被动回复（带 msg_id），与已验证的群发图/唱歌同路径。

## 6. 诚实边界

- **真 @**：主动群消息仍然只是「@名字」文字（群成员表接口 11253 无权限），
  回执里已明确说明，代码没有假装真 @。
- **群权限**：主动富媒体（无 msg_id）的平台权限未做线上验证；失败会如实回报。
- **日志矛盾**：问题三的「只回文字」与 `live.log` 里的「已发送图片 1/1」不一致，
  只能按“模型选择不稳定”处理；本次把它变成确定性行为，不宣称复现了原故障。
- **启发式**：`detectStickerRequest` 与解析规则是规则匹配，可能漏判/误判；
  误判时最坏结果是多发或漏发一张表情包，不会把动词残片当消息发出去。
