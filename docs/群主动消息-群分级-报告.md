## 二、主动消息的设计（以及为什么这么选）

### 流程

```
主人私聊：「在群里卖个萌」
   ↓
parsePendingInstruction → 待办（独立 JSON，不占 historyTurns）
   ↓
立即解析目标群（群注册表：any / 大群 / 小群 / 显式 group:<id>）
   ↓
查本地配额账本（平台硬限制 + 功能自限）
   ↓
POST /v2/groups/{gid}/messages（不带 msg_id = 主动消息）
   ↓
成功 → markDone + 回执说「已经发到群里（哪个群、多大、依据）」
失败 → markAttempt + 回执如实说「没发出去（原因）」，绝不假装
```

### 决策 1：立刻发，不等

- **默认 `QQ_PENDING_DELIVERY=proactive`**：创建后同一轮就发，回执里直接带结果。
- 不做「延迟几秒给反悔窗口」：延迟会让结果无法在同一条回执里说清，必须再发一条私聊主动消息
  （多烧一次配额、还多一条打扰），而且进程重启会丢定时器。**立刻发 + 在回执里说清发到哪个群**
  比「几秒后可反悔」更可靠。
- 保留 `deferred` 模式（旧行为，等主人到群里说话），一条环境变量即可切回。

### 决策 2：不做二次确认，但把「发到哪」说清楚

- 每一条回执都写：**群 id 短码 + 大/小群 + 人数依据**。
- 「去大群/小群」/「只说了群里」由确定性规则选群，不消耗模型额度。
- 只有在**无法确定目标**时才不发并说明：不知道有哪些群 / 没有符合条件的大群/小群。

### 决策 3：失败必须如实，且保留兜底

- 平台拒发（权限/频控/不在群/禁言/违规/重复）→ 回执写人话原因，`pending` 保留（最多重试 3 次），
  主人之后在群里说话时，仍可用**被动回复**补上（不烧主动配额）。
- 配额到顶 → **不发**，回执写「今天自限额度用完了」。
- 不知道群 → **不瞎发**，回执给明确办法：「主人在群里说一声，春禾立刻做」。
- 绝不允许模型把「没发出」说成「已经发了」：成功/失败文案由代码生成，且额外给模型一条
  `describeProactiveDeliveryForModel` 提示，失败时明确禁止说「已经发了」。

### 决策 4：配额（发前查、发后记、落盘）

`src/core/proactive-quota.js` → `data/proactive-quota.json`

| 层 | 默认 | 说明 |
| --- | --- | --- |
| 平台/单群/天 | 1000 | 官方文档 |
| 平台/单群/分钟 | 20 | 官方文档 |
| 功能自限/天 | 20 | 只作用于「私聊指令→群主动消息」，防刷屏 |
| 提醒阈值 | 80% | 回执里提示「快到期了」 |

- 每次发送（成功或失败）都记账，**重启不清零**；
- 失败的尝试也算（平台通常也计数），保守起见按 attempts 计；
- 原子写盘（tmp + rename），当天/分钟按本地时区统计。

### 决策 5：哪些动作能主动发？

| kind | 主动发？ | 说明 |
| --- | --- | --- |
| `cute`（卖萌/比心/撒娇） | ✅ | 确定性文案「主人～春禾来卖个萌啦 💖 啾咪～」 |
| `say`（说一句晚安） | ✅ | 发主人指定那句话 |
| `at`（@某人） | ✅（文字） | 发「@名字 主人让春禾来叫你一下～」；群成员表不可用，不保证是真 @ |
| `generic` | ❌ 走 deferred | 不让模型现编一句话发到群里（可能带上私聊上下文/不合适内容） |
| `sing` | ❌ 走 deferred | 主动唱会占 GPU/曲库管道；且当前 GPU 被 RVC 训练占用 |

## 三、大小群分级

### 数据源与标注

`src/core/groups.js` → `data/groups.json`

| 来源 | 字段 | 含义 |
| --- | --- | --- |
| `source:"api"` | `memberCount` | 接口返回的真实人数（当前应用无权限，基本不会出现） |
| `source:"observed"` | `observedCount` | 记忆里 `group:<gid>:<uid>` 中**说过话的不同人**数量，**只是下限** |

- `lowerBound:true`、`confidence:"lower_bound"` 明确标注；
- 回执里写「至少 N 位发言人；成员数接口无权限，按下限估算」，不写成「N 人」；
- 接口返回空（`[]`）时**不写 0 人**，不覆盖已有 observed；
- 启动时从 `memory.json` 播种；运行中每条群消息 `observe` + `addMessages`；
- 记忆里的 mock 冒烟假群（`group-openid-1`，长度 < 16）会被过滤，避免「你在哪些群」多出一个假群。

### 阈值与理由

| 阈值 | 默认 | 理由 |
| --- | --- | --- |
| API 真人数 → 大群 | `>= 10` 人 | 10 人以下更像熟人小群/测试群 |
| observed 下限 → 大群 | `>= 5` 位发言人 | observed 系统性低估：真实样本里 **47 人的大群只观察到 8 位发言人**（约 17%）；另两个群只有 2 和 1 位。5 正好落在 2 与 8 的天然断层上 |

两者都可配：`QQ_GROUP_LARGE_THRESHOLD` / `QQ_GROUP_OBSERVED_LARGE_THRESHOLD`。

### 选群规则

| 主人说法 | 选法 |
| --- | --- |
| 「去大群做 X」 | 在 `sizeLabel=large` 的群里挑**最活跃**的（发言最多），不是人数最极端的 |
| 「去小群做 X」 | 在 `sizeLabel=small` 的群里挑**最活跃**的（真实数据里是 AB20，而不是只有 1 人的 90A0） |
| 「去群里做 X」（没点名） | 默认 `QQ_GROUP_DEFAULT_PICK=active`：挑最活跃的群（真实数据里是 9F42 主群）；可配 `small` 改为小群优先 |
| 显式 `群 <openid>` | 只用那个群；注册表没登记也照发（主人点名的） |

**为什么默认 active 而不是 small**：「群里」在对话里通常指「我们平时说话的那个群」；真实数据里 9F42 有 94 条发言、AB20 只有 32 条。发到一个小群但主人其实指的是主群，比发到主群更尴尬。且回执会写清发到哪个群，主人能立刻纠正。

### 注入人格

`ctx.groups`（仅主人）→ `describeGroupsForModel`：

```
【春禾在的群 · 系统清单】共 3 个（QQ 不提供群名，只有群 id）：
- 大群 AAAAAAAA…AAAA：至少 8 位发言人说过话（下限，不是真实人数）；发言 94 条
- 小群 BBBBBBBB…BBBB：至少 2 位发言人说过话（下限，不是真实人数）；发言 32 条
- 小群 CCCCCCCC…CCCC：至少 1 位发言人说过话（下限，不是真实人数）；发言 2 条
派活规则：
- 「去大群/小群」→ 系统按标签选群，回执说清发到哪个群；
- 只说「群里」→ 默认最活跃的群；
- 认不出符合条件的大群/小群 → 如实说，绝不拿别的群顶替；
- 被问「你在哪些群」→ 照清单回答，不要再说看不到群列表；
- 人数是下限时不要报成精确人数。
```

## 七、诚实报告：做不到 / 有风险的部分

1. **群成员真实人数拿不到**：`11253 无接口访问权限`。所有「大群/小群」在生产环境都是 observed 下限，
